# 移行テーブル定義におけるデータ型（議論用）

**位置づけ:** お客様との議論・方針整理用。実装手順、ETL設計、AI向け指示は対象外。  
**目的:** SQL Server → Snowflake のテーブル移行時にデータ型を誤らないこと。Structured Raw の後に CDC Raw へ進むと、型のやり直し（ALTER / 再作成 / 試験のやり直し）が極めて高いコストになるため、**移行テーブル文書の段階で型を確定**する。

---

## 1. 背景（お客様ご指摘）

手順書の指摘反映は完了済み。追加で相談された点は次のとおり。

- 変換ルールに**無いデータ型**が出たときの措置が無い。
- データ型は**テーブル**で特に慎重に設計したい。
- **View** は CREATE で型指定がなく、Snowflake 側で付与される。2次利用はほぼユーザ利用。
- **テーブル**はシステム処理に使われる。定義が誤ると試験が無駄になり、エラーの原因になる。
- 現状は Structured Raw。Raw + 継続 CDC になると、安易な ALTER はできない。

お客様案（限界として提示された手順）:

1. Qlik の変換規則をドキュメントレベルで確認する  
2. 保全環境で SQL Server DDL と Snowflake DDL を比較し、変換規則と矛盾がないことを確認する  
3. 変換表を作成して対応する  

ベトナム側に全部やってほしい、という話ではなく、意見を求められている。

---

## 2. 結論（議論で先に共有したいこと）

①②③は **移行テーブル文書に載せる変換表を作る手順として妥当**。賛成。

ただし、①②③だけでは「CDC開始後に型をやり直さない」ことまでは保証できない。不足は次の2点。

1. **変換表に無い型が現れたときの措置**（推測して作らない / 止めて確認する）  
2. **稼働後の型変更は ALTER しない**、という変更の扱い  

テーブルはシステム利用のため、型は「後で直すもの」ではなく **契約** として文書に書く。View は推論型でよく、同じ厳しさは不要。

この文書のゴールは、実装ではなく、**移行テーブル文書に何を書くか・どこまで確認すれば型ミスを防げるか**をお客様と揃えること。

お客様①②③を具体化する案として、下記の手順を提案する（§3）。

## 3. 提案したい手順

お客様の①②③に賛成したうえで、変換表を「漏れなく・Qlikと矛盾なく」作る手順として次を提案する。

### 3.1 案（お客様に出す形）

1. **現行 SQL Server の CREATE TABLE（DDL）を読み、使用中データ型を一覧する**  
2. **Qlik / CDC 移行の公式ドキュメントを読み、定義されているデータ型（と変換先）を一覧する**  
3. **1 と 2 を突合し、型の集合を整理する**（マージ＝差分が見えるようにする）  
4. **Snowflake 公式は「制約の確認」に使う**（Qlik が出す型が Snowflake で存在するか、桁・精度の上限）。**SQL Server→Snowflake の変換の正は Qlik とする**  
5. **3 の型一覧に、2 の Qlik 変換を当てて変換表を作る**  
6. **（お客様②のまま）保全で SQL Server DDL と Snowflake 実測 DDL を比較し、5 と矛盾がないか確認する**  
7. **変換表に無い型はテーブルを作らない（確認待ち）。CDC後の既存列型変更は原則 ALTER しない**

1〜5 が「変換表の作り方」。6〜7 が「CDC後にやり直さないための閉じ」。

### 3.2 元案との違い（内部メモ。お客様には短くでよい）

元の5ステップ案:

1. SQL Server DDL から型一覧  
2. Qlik/CDC ドキュメントから型一覧  
3. 1 と 2 を比較してマージ  
4. Snowflake 公式の SQL Server→Snowflake マッピングを一覧  
5. 3 と 4 で変換表を作る  

**1〜3 は良い。** お客様①より先に「実際に使っている型」を取るので、変換ルール外の型（今回の指摘漏れ）が見える。

**4 と 5 は直した方がよい。** 変換の正を Snowflake 公式（SnowConvert 等）にすると、Qlik CDC が実際に書く型とずれる。ずれたテーブルを Structured Raw で試験しても、CDC Raw でエラーまたは再定義になる。今回避けたい再作業そのもの。

例（ドキュメントが食い違うところ）:

| SQL Server | Snowflake公式寄りの型 | Qlik が出しがちな型 |
|---|---|---|
| `DATETIMEOFFSET` | `TIMESTAMP_TZ` | `STRING` → `VARCHAR` |
| `TIME` | `TIME` | `STRING(16)` → `VARCHAR` |
| `INT` | `NUMBER(10,0)` 等 | `NUMBER(38,0)` |
| `TIMESTAMP`（rowversion） | 日時と誤解しやすい | バイナリ |

CDC で載せるなら **Qlik の型が正**。Snowflake 公式は「その型で CREATE できるか・桁上限は何か」のチェックに使う。

**3 の「マージ」** は、1つのリストに足すだけではなく、分類する。

| 分類 | 意味 | 変換表 |
|---|---|---|
| 1 にも 2 にもある | 使用中かつ Qlik 定義あり | 通常行（Qlik変換を採用） |
| 1 だけにある | **使用中だが変換ルール外** | **停止。推測しない。** 今回の指摘漏れの本体 |
| 2 だけにある | Qlikにあるが現行DDL未使用 | 参考行。今はテーブルに使わない。将来用 |

「全部マージして Snowflake 公式で型を決める」だと、ルール外の型が VARCHAR 等に飲み込まれ、停止措置が消える。

**6 が必要。** ドキュメント同士の比較（1〜5）だけでは、Qlikタスクの実測と違うことがある。お客様②（保全の実測DDL）は残す。

### 3.3 お客様①②③との対応

| お客様 | 本提案 |
|---|---|
| （なし → 今回の漏れを見つける手順） | 1. 現行DDLの型棚卸し |
| ① Qlik変換規則の確認 | 2. Qlik/CDCドキュメントの型と変換先 |
| （①の漏れ検出） | 3. 突合・分類（使用中 / ルール外 / 未使用） |
| （変換先の制約） | 4. Snowflake公式は制約チェックのみ |
| ③ 変換表 | 5. Qlik変換で変換表を作成 |
| ② 保全DDL比較 | 6. 実測で 5 を検証 |
| （指摘漏れの措置） | 7. ルール外は停止。CDC後は型ALTERしない |

ベトナム側で全部の型を決める、ではない。1〜3・5 の下書きと 6 の突合はできる。4 の「正はQlik」と 7 の停止はお客様に方針として判断していただく。

## 4. なぜ今の文書で型を固めないとやり直しになるか

| 段階 | 型を間違えたときの影響 |
|---|---|
| Structured Raw（再作成しやすい） | テーブル作り直し・試験やり直しで済むことが多い |
| CDC Raw（継続連携） | 既存列の型変更は適用プロセス・履歴データ・下流システムに影響。ALTER ができない、または再作成＋バックフィルになる |

やり直しの典型:

- 試験は通ったが、本番 CDC で型不一致エラー  
- `DATETIMEOFFSET` を日時型だと思って作り、Qlik は文字列で送ってくる  
- `TIMESTAMP`（SQL Server の rowversion）を日時型にしてしまう  
- 桁・精度不足で後から `VARCHAR(50)` → `(200)` や `NUMBER` の精度変更が必要になる  
- 変換表に無い型を仮で `VARCHAR` にしてしまい、システム処理が壊れる  

**移行テーブル文書で型を確定し、CDC開始後は原則その型を変えない。** これが再作業を避ける条件。

## 5. テーブルと View（文書上の扱いを分ける）

お客様の整理に同意する。移行テーブル文書でも対象を分ける。

### テーブル（システム利用・CDC対象）

- CREATE で型を明示する。  
- 変換表に載っている型だけを使う。  
- 誤り = システムエラー・試験無駄・CDC後のやり直し。  
- **文書の主対象。ここで慎重に設計する。**

### View（ユーザ2次利用）

- CREATE で型指定が無く、Snowflake が推論する。  
- 2次利用はほぼユーザ。推論のずれは不便だが、システム停止にはなりにくい。  
- 移行テーブル文書では「View の型は推論に任せる。テーブルと同等の変換表レビューはしない」と明記すれば十分。

同じ工数を View に使わない。議論の焦点はテーブル。

## 6. お客様手順 ①②③ で足りる範囲 / 足りない範囲

| 手順 | カバーできること | カバーできないこと |
|---|---|---|
| ① Qlik変換規則（ドキュメント） | 公式のデフォルト変換 | タスク個別の上書き、版差、ドキュメントと実測の差、「載る」と「意味が正しい」の差 |
| ② 保全の DDL 比較 | **今その環境にある型**が規則と矛盾しないこと | まだ出ていない型、保全に無いスキーマ、今後 CDC で増える列・型 |
| ③ 変換表 | テーブル定義時の参照表。JP/VN の共通言語 | 表に無い型の運用、CDC開始後の差分 |

②は必要。ただし「保全にある型の証明」であり、「将来の全型の証明」ではない。CDC Raw では将来の型を ALTER で吸収できないので、文書に **例外時の措置** を書いておく必要がある。

## 7. 移行テーブル文書に書くべきこと（提案）

実装ではなく、**文書の目次案**。これが揃えば型ミスの再作業を相当減らせる。

### 7.1 変換の正（優先順位）

矛盾したとき、どれを採用するか文書に書く。

1. 承認済みの個別例外（列単位）  
2. 保全環境の実測 DDL（Qlik が実際に出した型）  
3. Qlik 公式変換規則に基づく変換表  
4. 表に無い → **作らない（確認待ち）**

公式と保全が違う場合: 保全を「事実」として記録し、採用型は承認者が決める。第三の型をその場で invent しない。

### 7.2 変換表（③の本体）

人間が埋める表。ツール用YAMLではない。

| SQL Server型 | Qlik内部型 | Snowflake型 | 桁・精度の決め方 | 注意（意味の欠落） | 確度 | テーブル使用 |
|---|---|---|---|---|---|---|
| 例: `INT` | INT4 | `NUMBER(38,0)` | 固定 | Qlikは整数を NUMBER(38,0) | 問題なし | 可 |
| 例: `DATETIMEOFFSET` | STRING | `VARCHAR` | 長さは保全で確認 | タイムゾーン付き日時ではない | 要確認 | 可（Qlik準拠） |
| 例: `SQL_VARIANT` | 非サポート | （なし） | — | — | 停止 | 不可 |

確度の意味:

- **問題なし** … 変換表どおり定義してよい  
- **要確認** … 載るが意味・桁にリスク。初出はお客様確認  
- **停止** … 変換表に定義しない。テーブルを作らない  

### 7.3 変換ルール外の措置（今回不足している箇所）

テーブル:

- 変換表に無い型は **推測しない**（`VARCHAR` / `VARIANT` への仮置きもしない）。  
- 該当テーブルは定義を止め、変換表を更新・承認してから作成する。  
- 理由: 仮置きすると試験が通り、CDC後に本修正ができなくなる。

View:

- 推論または警告付きフォールバックを許容してよい（方針として文書に一行書けば足りる）。

### 7.4 CDC開始後の型変更（やり直し防止）

移行テーブル文書に「作った後」も一行で縛る。

- 既存列の **型変更・桁縮小・NOT NULL 強化は原則禁止**。必要なら新列追加または再作成＋バックフィル（変更管理）。  
- 列追加（NULL可）と VARCHAR の桁拡大は、Qlik / Snowflake の確認後に検討可。  
- ソースに新しい未知型の列が付いた場合も、作成時と同じ: **推測して ALTER しない。止めて確認。**

### 7.5 対象範囲の明記

- どのDB・スキーマが in-scope か。  
- 保全がその全部を含むか。含まないなら ②は「サンプル確認」と書く（全件証明と書かない）。  
- View は型レビュー対象外、と書く。

## 8. 間違えやすい型（文書の「注意」列に残すもの）

全部を暗記する必要はない。変換表の注意列用。Qlik の規則を正とする（Snowflake移行ツールの別マッピングと混ぜない）。

システム処理・CDCで特に事故りやすいもの:

| SQL Server | やりがちな誤り | 議論上の扱い（Qlik準拠の方向） |
|---|---|---|
| `TIMESTAMP` / `ROWVERSION` | 日時型にしてしまう | 日時ではない。バイナリ系 |
| `DATETIMEOFFSET` | `TIMESTAMP_TZ` と決め打ち | Qlikは STRING になり得る。公式＋保全で確認 |
| `TIME` | Snowflake `TIME` と決め打ち | Qlikは STRING になり得る。公式＋保全で確認 |
| `DATETIME` / `DATETIME2` | 精度・タイムゾーンを無視 | 精度を変換表に書く |
| `MONEY` / `SMALLMONEY` | 汎用 NUMBER で桁を落とす | 精度（19,4 等）を表に固定 |
| `DECIMAL`/`NUMERIC` の精度 | p>38 を黙って文字列化 | テーブルでは黙って替えない。確認 |
| `VARCHAR(MAX)` / `NVARCHAR(MAX)` / `XML` | 桁・LOB のCDC制限を無視 | 要確認。QlikでCLOB有効が必要かも |
| `UNIQUEIDENTIFIER` | BINARY と VARCHAR が混在 | 変換表で一方に固定 |
| `BIT` | NUMBER(1) と BOOLEAN が混在 | 変換表で一方に固定 |
| UDT（ユーザ定義型） | 名前のまま未定義 | 基底型に戻してから変換表を見る。戻せなければ停止 |
| `SQL_VARIANT` / `CURSOR` / `TABLE` | 適当に VARIANT | Qlik非サポートなら **停止** |
| `GEOGRAPHY` / `GEOMETRY` / `HIERARCHYID` | Snowflake地理型へ勝手に合わせる | 公式＋保全。勝手に最適化しない |

ポイント: 「Snowflakeとして綺麗な型」より **Qlikが実際に出す型** を移行テーブル文書の正とする。ここがずれると、テーブルは正しく見えても CDC で落ちる / 試験が無駄になる。

## 9. 「全ケースをカバーする」の意味

型を40個列挙しても、41個目は出る。全ケースカバーは次の5つが文書にあれば足りる。

1. **既知の型** → 変換表（①②③ + 利用中型の棚卸し）  
2. **未知の型** → 停止して確認（推測しない）  
3. **後から型が変わる** → ALTERしない。変更管理  
4. **載るが意味が違う** → 変換表の「要確認」＋保全実測  
5. **保全に無い対象** → in-scope 外、またはサンプルと明記  

型名の百科事典より、**41個目の型の行き場** を文書に書く方が再作業防止になる。

利用中型の棚卸し（①の前にやると漏れが減る）:

- SQL Server の利用中データ型を一覧する（テーブル列の distinct type）。  
- その一覧がすべて変換表に載っているか見る。  
- 保全に無い型が in-scope にあれば、②だけでは不足、と分かる。

（棚卸しSQLをこの議論で実装する必要はない。方針として「変換表の対象は実在型から取る」と書けばよい。）

## 11. お客様に確認したいこと（議論アジェンダ）

実装の話ではなく、移行テーブル文書に書くための確認。

1. 下記の変換表作成手順でよいか（お客様①②③の具体化）。  
   - SQL Server 現行DDLから使用中型を一覧  
   - Qlik/CDC公式から定義型と変換先を一覧  
   - 突合して「使用中」「ルール外」「未使用」に分ける  
   - Snowflake公式は制約確認のみ（変換の正はQlik）  
   - Qlik変換で変換表を作成  
   - 保全の実測DDLで検証  
2. テーブルで変換表に無い型は **停止（推測しない）** でよいか。View は推論でよいか。  
3. 公式と保全が違うとき、保全実測を優先してよいか。  
4. 保全は in-scope 全スキーマを含むか。含まないなら ②をサンプルと書くか。  
5. 要確認型（TIME、DATETIMEOFFSET、MONEY、MAX、XML 等）の承認者は誰か。  
6. CDC開始後、既存列の型変更は禁止、で文書に書いてよいか。  
7. 変換の正は Qlik 規則か。Snowflake 側の別マッピング（綺麗な型）へ寄せない、でよいか。

このうち **手順の「ルール外の分類」と 2・6** が、今回の「指摘漏れ」に対する答えになる。

## 12. 移行テーブル文書への追記案（合意後にそのまま貼れる文）

### データ型の対象

- 本節の対象は **テーブル** とする。View は CREATE 時に型指定がなく Snowflake が付与するため、変換表のレビュー対象外とする。

### 変換手順

1. 現行 SQL Server の CREATE TABLE から、使用中データ型を一覧する。  
2. Qlik / CDC 公式ドキュメントから、定義されているデータ型と変換先を一覧する。  
3. 1 と 2 を突合し、「使用中かつ定義あり」「使用中だがルール外」「定義のみ（未使用）」に分ける。  
4. Snowflake 公式は、Qlik の変換先が Snowflake で使えるか（桁・精度上限）の確認に使う。変換の正は Qlik とする。  
5. 3 に 2 の変換を当てて変換表を作成する。ルール外は行を「停止」とする。  
6. 保全環境で SQL Server DDL と Snowflake 実測 DDL を突合し、変換表と矛盾がないことを確認する。

### 変換ルール外のデータ型

- テーブルは、変換表に定義のないデータ型を推測して作成しない。  
- 検知した場合は当該テーブルの定義を止め、変換表の更新と承認後に作成する。  
- View は型推論を許容する。

### CDC開始後

- 既存列の型変更・桁縮小は原則として実施しない。  
- 必要な場合は変更管理（列追加または再作成）とする。  
- Raw＋継続CDCでは安易な ALTER は行わない。

> 2. Qlik/CDC公式から、定義されているデータ型と変換先を一覧する  
> 3. 1と2を突合し、「使用中」「ルール外（1のみ）」「未使用（2のみ）」に分ける  
> 4. Snowflake公式は制約（その型が使えるか、桁上限）の確認に使う。SQL Server→Snowflakeの変換の正はQlikとする  
> 5. 3にQlik変換を当てて変換表を作成する  
> 6. 保全の実測DDLで5を検証する（②のまま）  
>
> 4をSnowflake公式のマッピング自体にしてしまうと、Qlik CDCが実際に出す型（例: DATETIMEOFFSETやTIMEがSTRINGになる等）とずれ、CDC開始後のやり直しになるリスクがあります。  
> 3で「ルール外」が見えることが、今回不足している措置の前提になります。ルール外は推測せず、テーブル作成を止めて確認する案です。Viewは従来どおり推論でよいと思います。  
> CDC開始後の既存列の型変更は原則ALTERしない、も文書に書いておくと再作業を防げます。
>
> 変換表の下書きと突合は進められます。変換の正をQlikにする点と、ルール外を停止にする点だけ、方針としてご判断いただきたいです。

短い口頭用:

> ①②③は賛成です。具体化として、まず現行DDLとQlik資料で型を突合し、ルール外を見つけます。変換の正はQlikで、Snowflake公式は桁などの制約確認だけにします。表に無い型は作らず、CDC後は型をALTERしない、を提案します。

---

## 14. この議論でやらないこと

- ETL / Qlikタスク / Snowflake DDL の実装  
- AI Agent 用の仕様やプロンプト  
- 変換表の全行をこの場で埋めること（Qlik版と保全DDLが必要）  
- View の型をテーブルと同じ粒度で設計すること  

合意できたら次は、移行テーブル文書へ §12 を反映し、§3 の手順で変換表を埋める。それまで型を仮決めしてテーブルを量産しない。
