# 移行テーブル定義におけるデータ型（議論用）

**位置づけ:** お客様との議論・方針整理用。実装手順、ETL設計、AI向け指示は対象外。  
**目的:** SQL Server → Snowflake のテーブル移行時にデータ型を誤らないこと。Structured Raw の後に CDC Raw へ進むと、型のやり直し（ALTER / 再作成 / 試験のやり直し）が極めて高いコストになるため、**移行テーブル文書の段階で型を確定**する。

---

## 1. 背景（お客様ご指摘）

手順書の指摘反映は完了済み。追加で相談された点は次のとおり。

- 変換ルールに**無いデータ型**が出たときの措置が無い。
- データ型は**テーブル**で特に慎重に設計したい。
- **View** は CREATE で型指定がなく、Snowflake 側で付与される。2次利用はほぼユーザ利用。
- **テーブル**はシステム処理に使われる。定義が誤ると試験が無駄になり、エラーの原因になる。
- 現状は Structured Raw。Raw + 継続 CDC になると、安易な ALTER はできない。

お客様案（限界として提示された手順）:

1. Qlik の変換規則をドキュメントレベルで確認する  
2. 保全環境で SQL Server DDL と Snowflake DDL を比較し、変換規則と矛盾がないことを確認する  
3. 変換表を作成して対応する  

ベトナム側に全部やってほしい、という話ではなく、意見を求められている。

---

## 2. 結論（議論で先に共有したいこと）

①②③は **移行テーブル文書に載せる変換表を作る手順として妥当**。賛成。

ただし、①②③だけでは「CDC開始後に型をやり直さない」ことまでは保証できない。不足は次の2点。

1. **変換表に無い型が現れたときの措置**（推測して作らない / 止めて確認する）  
2. **稼働後の型変更は ALTER しない**、という変更の扱い  

テーブルはシステム利用のため、型は「後で直すもの」ではなく **契約** として文書に書く。View は推論型でよく、同じ厳しさは不要。

この文書のゴールは、実装ではなく、**移行テーブル文書に何を書くか・どこまで確認すれば型ミスを防げるか**をお客様と揃えること。

お客様①②③を具体化する案として、下記の手順を提案する（§3）。

---

## 3. 提案したい手順

お客様の①②③に賛成したうえで、変換表を「漏れなく・Qlikと矛盾なく」作る手順として次を提案する。

### 3.1 案（お客様に出す形）

1. **現行 SQL Server の CREATE TABLE（DDL）を読み、使用中データ型を一覧する**  
2. **Qlik / CDC 移行の公式ドキュメントを読み、定義されているデータ型（と変換先）を一覧する**  
3. **1 と 2 を突合し、型の集合を整理する**（マージ＝差分が見えるようにする）  
4. **Snowflake 公式は「制約の確認」に使う**（Qlik が出す型が Snowflake で存在するか、桁・精度の上限）。**SQL Server→Snowflake の変換の正は Qlik とする**  
5. **3 の型一覧に、2 の Qlik 変換を当てて変換表を作る**  
6. **（お客様②のまま）保全で SQL Server DDL と Snowflake 実測 DDL を比較し、5 と矛盾がないか確認する**  
7. **変換表に無い型はテーブルを作らない（確認待ち）。CDC後の既存列型変更は原則 ALTER しない**

1〜5 が「変換表の作り方」。6〜7 が「CDC後にやり直さないための閉じ」。

### 3.4 7ステップの説明（議論用）

流れのイメージ:

```
SQL Server 現行DDL        Qlik/CDC 公式
      │                        │
      │ ① 使用中の型           │ ② 定義されている型と変換先
      └──────────┬─────────────┘
                 │ ③ 突合・分類
                 │    A 使用中かつ定義あり
                 │    B 使用中だがルール外  ← 今回の指摘漏れ
                 │    C 定義のみ（未使用）
                 ▼
        ④ Snowflake公式で制約確認
           （型が存在するか、桁・精度の上限）
           ※ 変換の正は Qlik。Snowflake公式で型を決めない
                 ▼
        ⑤ 変換表を作成（AはQlik変換、Bは停止、Cは参考）
                 ▼
        ⑥ 保全の実測DDLで検証（お客様②）
                 ▼
        ⑦ ルール外は作らない / CDC後は型をALTERしない
```

対象は **テーブルのみ**。View はこの7ステップの外（型はSnowflakeが推論する）。

---

#### Step 1 — 現行 SQL Server DDL から使用中データ型を一覧する

**何をするか**  
in-scope の `CREATE TABLE`（または同等のカタログ情報）を読み、**今テーブルで使っているデータ型**を重複なく一覧する。テーブル名の一覧ではなく、**型の種類**（`INT`, `NVARCHAR(n)`, `DATETIME2`, `XML` …）と、必要なら桁・精度の最大値。

**なぜ必要か**  
Qlik資料だけ見ても「うちのシステムで本当に使っている型」は分からない。お客様が指摘した「変換ルールに無い型」は、**現行DDLにあって Qlik資料に無い型**として初めて見える。棚卸しが無いと、変換表は「資料に載っている型」だけになり、本番の1テーブルで未知型が出て止まる／仮型にしてCDC後にやり直す。

**見るもの（例）**

- 対象DB・スキーマの CREATE TABLE  
- 列の型、長さ、精度、NULL、IDENTITY、計算列、UDT（ユーザ定義型は基底型も）  
- View の CREATE は型一覧の対象にしない（推論のため）

**成果物（文書に残す）**

| SQL Server型 | 使用列数 | 桁・精度の範囲（例） | 出現テーブル例 |
|---|---|---|---|
| `INT` | 120 | — | Customer, Order |
| `NVARCHAR` | 80 | 10〜4000 | … |
| `DATETIMEOFFSET` | 3 | scale 7 | … |
| `SQL_VARIANT` | 1 | — | Legacy.X |

**議論ポイント**

- in-scope はどのDB・スキーマまでか。保全に全部入っているか。  
- UDT は基底型に分解して数えるか。分解できないものは Step 3 の「ルール外」。  
- 「現行」は Structured Raw 対象の今のDDLか。将来CDCに入る予定テーブルも含めるか（含めないと Step 1 がサンプルになる）。

**飛ばすと**  
変換表が机上の型だけになり、今回の指摘漏れ（ルール外）を見つけられない。

---

#### Step 2 — Qlik / CDC 公式から、定義されている型と変換先を一覧する

**何をするか**  
Qlik（Replicate または実際に使う製品・バージョン）の公式で、SQL Server ソース型 → Qlik内部型 → Snowflake ターゲット型、を書き写す。型名のリストだけではなく **変換先** まで取る。

Qlik は二段変換になる:

```
SQL Server 型  →  Qlik 内部型  →  Snowflake 型
例: INT        →  INT4         →  NUMBER(38,0)
例: TIME       →  STRING(16)   →  VARCHAR(16)
例: DATETIMEOFFSET → STRING    →  VARCHAR
```

**なぜ必要か**  
お客様①そのもの。CDCで Snowflake に載る型は、Snowflake移行ガイドではなく **Qlikが変換した結果**。ここを正にしないと、テーブル定義とCDC適用が食い違う。

**見るもの**

- 使用中の Qlik 製品名とバージョン（ここを文書に明記。版で表が変わる）  
- SQL Server source data types  
- Snowflake target data types  
- 非サポート型（Qlikが `SQL_VARIANT` 等を unsupported と書いているか）  
- LOB（`VARCHAR(MAX)`, `XML` 等）をタスクで有効にする必要がある、という注記

**成果物**

| SQL Server型 | Qlik内部型 | Snowflake型（Qlikデフォルト） | 公式の注記 |
|---|---|---|---|
| `INT` | INT4 | `NUMBER(38,0)` | 整数は NUMBER(38,0) |
| `TIME` | STRING(16) | `VARCHAR(16)` | 日時型TIMEではない |
| `SQL_VARIANT` | 非サポート | （なし） | ルール外扱い |

**議論ポイント**

- 製品は Replicate か、別の Qlik CDC か。バージョンは。  
- タスクで型の上書き（グローバル変換）をしているか。しているなら公式デフォルトではなく **その設定** が正。  
- 非サポートと書いてある型を、Snowflake側で無理に持つ予定があるか（原則持たない）。

**飛ばすと**  
「Snowflakeとして正しい型」でテーブルを作り、Qlikが別の型で書いて試験・CDCが無駄になる。

---

#### Step 3 — Step 1 と Step 2 を突合し、分類する（マージではない）

**何をするか**  
1 の「使っている型」と 2 の「Qlikが定義している型」を突き合わせ、**3種類に分ける**。1つのリストに足して終わり、ではない。

| 分類 | 条件 | 意味 | この後 |
|---|---|---|---|
| **A. 使用中かつ定義あり** | 1 にも 2 にもある | 普通に変換表へ載せる | Step 5 で Qlik変換を採用 |
| **B. 使用中だがルール外** | **1 だけにある** | 今のテーブルで使っているが、Qlik文書に変換が無い／非サポート | **今回お客様が指摘した漏れの本体。** Step 7 で停止。仮のVARCHARにしない |
| **C. 定義のみ（未使用）** | 2 だけにある | Qlikにはあるが現行DDLに無い | 変換表の参考行。今はCREATEしない。将来その型が出たら A と同じ手順 |

**なぜ必要か**  
「全部マージしてマッピングする」だと B が A に紛れる。B こそ、推測してテーブルを作るとCDC後にやり直せない型。分類して初めて「措置」を書ける。

**成果物（議論の中心資料）**

例:

| 分類 | SQL Server型 | 判断 |
|---|---|---|
| A | `INT`, `NVARCHAR`, `DATETIME2` | 変換表へ |
| B | `SQL_VARIANT`, 分解できないUDT | 停止。お客様判断 |
| C | Qlikにあるが未使用の型 | 参考 |

**議論ポイント**

- B をどうするか（提案: テーブル作成を止めて確認。VARCHAR仮置きはしない）。  
- B の列をCDC対象から外す、という選択肢もある（対象外にするなら文書に明示）。  
- C を変換表に全部書くか、使うとき追加するか（提案: 参考として残し、使うとき A に昇格）。

**飛ばすと**  
ルール外の措置がまた無くなる。お客様の指摘に答えられない。

---

#### Step 4 — Snowflake 公式は「制約確認」だけ。変換の正は Qlik

**何をするか**  
Step 2 で得た **Qlikの変換先型** について、Snowflake 公式で次だけ確認する。

- その型は Snowflake に存在するか  
- 桁・精度・サイズの上限（例: `NUMBER` は精度38まで、`VARCHAR` は 16MB、`BINARY` 上限）  
- 上限を超える場合、Qlik資料がどう書いているか（黙ってTEXTにする、切る、エラー）と、**テーブルとしてどうするか**

**しないこと**  
Snowflake公式（SnowConvert 等）の「SQL Server → Snowflake 推奨マッピング」で、Qlikと違う型に**置き換えない**。

| SQL Server | Snowflake公式寄り（使わない） | Qlik（正にする） | なぜQlikか |
|---|---|---|---|
| `DATETIMEOFFSET` | `TIMESTAMP_TZ` | `VARCHAR`（STRING） | CDCが文字列で書く。TZ型で作ると型不一致 |
| `TIME` | `TIME` | `VARCHAR(16)` | 同上 |
| `INT` | `NUMBER(10,0)` など | `NUMBER(38,0)` | Qlikの整数ルール |
| `TIMESTAMP`（rowversion） | 日時と誤解しやすい | `BINARY(8)` | SQL ServerのTIMESTAMPは日時ではない |

**なぜ必要か**  
Snowflake公式は「SQLを綺麗に移植する」資料。本案件は「Qlik CDCがSnowflakeに書く」。正が二つあると変換表が割れ、テーブルを二度作ることになる。

Snowflake公式を見る意味は残る: Qlikが `NUMBER(p,s)` で p>38 のような、**Snowflakeが受けられない組み合わせ**を、作成前に見つける。見つけたら「Snowflake公式に合わせて型を変える」のではなく、「この列はどうするか」をお客様と決める（対象外、別連携、確認待ち）。

**成果物**

- Qlik変換先ごとに「Snowflakeで作成可能 / 上限注意 / 作成不可」の印  
- 作成不可・上限超えは Step 5 で「要確認」または「停止」

**議論ポイント**

- 変換の正を Qlik にしてよいか（ここが方針の核心）。  
- 「Snowflakeとして綺麗な型の方がシステム処理に良い」という意見が出たら: 綺麗な型は **CDCの後段（加工層）** でやる。RawテーブルはQlikに合わせる。Rawを綺麗にするとCDCが壊れる。  
- 上限超え（DECIMAL p>38 等）を黙ってVARCHARにするか、止めるか（提案: テーブルでは止め、確認する）。

**飛ばすと**  
Qlikが出す型がSnowflake上限を超えて CREATE できない、または逆に Snowflake推奨で作ってCDCが合わない。

---

#### Step 5 — 分類結果と Qlik変換から、変換表を作る

**何をするか**  
お客様③。Step 3 の A/B/C と Step 2 の変換、Step 4 の制約を、**人が読む変換表**にする。これが移行テーブル文書の本体。

**行の作り方**

- **A** … SQL Server型、Qlik内部型、Snowflake型、桁の決め方、注意、確度＝問題なしまたは要確認  
- **B** … Snowflake型は空。「停止」。措置は Step 7  
- **C** … 参考。今のCREATE対象外  

確度:

- **問題なし** … そのままテーブル定義に使ってよい  
- **要確認** … Qlik上は載るが、意味や桁にリスク（TIME、DATETIMEOFFSET、MONEY、MAX、XML 等）。初出はお客様確認  
- **停止** … B、または Step 4 で作成不可  

**成果物（変換表の列案）**

| SQL Server型 | 分類A/B/C | Qlik内部型 | Snowflake型 | 桁・精度 | Snowflake制約 | 注意 | 確度 |
|---|---|---|---|---|---|---|---|
| `INT` | A | INT4 | `NUMBER(38,0)` | 固定 | 可 | 整数は38,0 | 問題なし |
| `TIME` | A | STRING(16) | `VARCHAR(16)` | 16 | 可 | 時刻型ではない | 要確認 |
| `SQL_VARIANT` | B | 非サポート | （なし） | — | — | ルール外 | 停止 |

**議論ポイント**

- 要確認を誰が承認するか。  
- 桁（`NVARCHAR(100)` の 100 など）は型名だけでなく変換表にルールを書く。後から桁不足でALTERするとCDCで痛い。  
- この表は「列単位の例外」も足せるようにする（ほとんどの列は型単位、例外だけ列名）。

**飛ばすと**  
①②の確認が口頭で終わり、テーブル定義の正本が無い。人によって型が割れる。

---

#### Step 6 — 保全の実測DDLで変換表を検証する（お客様②）

**何をするか**  
保全で、同じテーブルについて:

- SQL Server の実際の列型  
- Snowflake に Qlik が作った／出した実際の列型  

を並べ、Step 5 の変換表と矛盾がないか見る。

**なぜ必要か**  
Step 1〜5 は **ドキュメントと現行DDL**。Qlikタスクの設定、バージョン、LOB有効、上書き規則で、公式と実測が違うことがある。CDC Raw では実測と違う型でテーブルを作ると適用エラーになる。お客様②は「机上の変換表を、動いている環境で検定する」ステップ。残す。

**見るもの**

- 保全の SQL Server DDL  
- 保全の Snowflake DDL（Qlikが触った後）  
- Step 5 の変換表

**結果の扱い（優先順位。文書に書く）**

1. 承認済みの列単位例外  
2. **保全の実測**（事実）  
3. Qlik公式に基づく変換表  
4. 表に無い → 作らない  

公式と保全が違うとき: 保全を事実として記録し、**採用する型はお客様が決める**。第三の型をその場で作らない。

**議論ポイント**

- 保全は in-scope 全スキーマを含むか。含まないなら Step 6 はサンプル検定、全件証明ではない、と書く。  
- 差が出たとき誰が採用を決めるか。  
- 保全にまだ Snowflake 側が無いテーブルは、Step 5 のみで仮置きせず、Qlik検証後に確定するか（提案: 要確認のまま残し、実測が出てから「問題なし」にする）。

**飛ばすと**  
文書どおりの型で Structured Raw を作り、保全・本番のQlik実測とずれてCDCでやり直す。

---

#### Step 7 — ルール外は作らない。CDC後は型をALTERしない

**何をするか**  
変換表の使い方と、作った後の禁則を移行テーブル文書に書く。手順1〜6の **閉じ**。ここが無いと、また「ルールに無い型の措置が無い」になる。

**7a. 変換表に無い型（分類B、または後から出てきた新型）**

テーブル（システム・CDC）:

- 推測しない。`VARCHAR` / `VARIANT` への仮置きもしない。  
- そのテーブルの定義を止める。変換表を更新し、承認してから作る。  
- 仮置きすると試験が通り、CDC開始後に本修正（ALTER）ができなくなる。

View:

- 型推論のままでよい（お客様の整理どおり）。

**7b. CDC開始後（Structured Raw → CDC Raw のあと）**

| 変更 | 原則 |
|---|---|
| 既存列の型変更 | しない（ALTERしない） |
| 桁縮小、NOT NULL強化 | しない |
| 列追加（NULL可） | 変更管理のうえ検討可 |
| VARCHAR桁拡大 | Qlik/Snowflake確認のうえ検討可 |
| ソースに未知型の新列 | 7aと同じ。推測してALTERしない |

必要なら新列追加、または再作成＋バックフィル（変更管理）。安易なALTERはしない。

**なぜ必要か**  
1〜6 は「今ある型の変換表」。CDCは継続する。明日ソースが型を足す。そのときの措置が文書に無いと、現場が仮型でALTERし、再作業になる。お客様の「RawになるとALTERできない」への直接の答え。

**成果物**  
移行テーブル文書の短文（停止ルール＋ALTER禁止）。変換表の「停止」行とセット。

**議論ポイント**

- 停止でよいか。止めたくない場合の代替（その列をCDC対象外にする）を認めるか。  
- ALTER禁止を文書に書いてよいか。例外（桁拡大だけ可、など）を先に決めるか。  
- 承認者は誰か。ベトナムは下書きまで、判断はお客様。

**飛ばすと**  
変換表はあっても、表に無い型とCDC後の差分で、また試験無駄・再作成になる。

### 3.5 議論で使う短い対応表

| Step | 一言 | お客様①②③ | 決めてほしいこと |
|---|---|---|---|
| 1 | 何を使っているか | （追加）ルール外を見つける | in-scope の範囲 |
| 2 | Qlikはどう変換するか | ① | 製品・バージョン、タスク上書きの有無 |
| 3 | ルール外を切り出す | （追加）指摘漏れの検出 | Bを停止にするか |
| 4 | Snowflakeは上限チェック | （追加）正を混ぜない | **正はQlikでよいか** |
| 5 | 変換表 | ③ | 要確認の承認者 |
| 6 | 実測で検定 | ② | 差が出たときの採用者、保全の範囲 |
| 7 | 作らない／ALTERしない | （追加）指摘漏れの措置 | 停止とALTER禁止を文書に書くか |

ベトナム: 1〜3・5 の下書き、6 の突合。  
お客様: 4 の「正はQlik」、3 の分類B、7 の停止とALTER禁止。

### 3.2 元案との違い（内部メモ。お客様には短くでよい）

元の5ステップ案:

1. SQL Server DDL から型一覧  
2. Qlik/CDC ドキュメントから型一覧  
3. 1 と 2 を比較してマージ  
4. Snowflake 公式の SQL Server→Snowflake マッピングを一覧  
5. 3 と 4 で変換表を作る  

**1〜3 は良い。** お客様①より先に「実際に使っている型」を取るので、変換ルール外の型（今回の指摘漏れ）が見える。

**4 と 5 は直した方がよい。** 変換の正を Snowflake 公式（SnowConvert 等）にすると、Qlik CDC が実際に書く型とずれる。ずれたテーブルを Structured Raw で試験しても、CDC Raw でエラーまたは再定義になる。今回避けたい再作業そのもの。

例（ドキュメントが食い違うところ）:

| SQL Server | Snowflake公式寄りの型 | Qlik が出しがちな型 |
|---|---|---|
| `DATETIMEOFFSET` | `TIMESTAMP_TZ` | `STRING` → `VARCHAR` |
| `TIME` | `TIME` | `STRING(16)` → `VARCHAR` |
| `INT` | `NUMBER(10,0)` 等 | `NUMBER(38,0)` |
| `TIMESTAMP`（rowversion） | 日時と誤解しやすい | バイナリ |

CDC で載せるなら **Qlik の型が正**。Snowflake 公式は「その型で CREATE できるか・桁上限は何か」のチェックに使う。

**3 の「マージ」** は、1つのリストに足すだけではなく、分類する。

| 分類 | 意味 | 変換表 |
|---|---|---|
| 1 にも 2 にもある | 使用中かつ Qlik 定義あり | 通常行（Qlik変換を採用） |
| 1 だけにある | **使用中だが変換ルール外** | **停止。推測しない。** 今回の指摘漏れの本体 |
| 2 だけにある | Qlikにあるが現行DDL未使用 | 参考行。今はテーブルに使わない。将来用 |

「全部マージして Snowflake 公式で型を決める」だと、ルール外の型が VARCHAR 等に飲み込まれ、停止措置が消える。

**6 が必要。** ドキュメント同士の比較（1〜5）だけでは、Qlikタスクの実測と違うことがある。お客様②（保全の実測DDL）は残す。

### 3.3 お客様①②③との対応

| お客様 | 本提案 |
|---|---|
| （なし → 今回の漏れを見つける手順） | 1. 現行DDLの型棚卸し |
| ① Qlik変換規則の確認 | 2. Qlik/CDCドキュメントの型と変換先 |
| （①の漏れ検出） | 3. 突合・分類（使用中 / ルール外 / 未使用） |
| （変換先の制約） | 4. Snowflake公式は制約チェックのみ |
| ③ 変換表 | 5. Qlik変換で変換表を作成 |
| ② 保全DDL比較 | 6. 実測で 5 を検証 |
| （指摘漏れの措置） | 7. ルール外は停止。CDC後は型ALTERしない |

ベトナム側で全部の型を決める、ではない。1〜3・5 の下書きと 6 の突合はできる。4 の「正はQlik」と 7 の停止はお客様に方針として判断していただく。

## 4. なぜ今の文書で型を固めないとやり直しになるか

| 段階 | 型を間違えたときの影響 |
|---|---|
| Structured Raw（再作成しやすい） | テーブル作り直し・試験やり直しで済むことが多い |
| CDC Raw（継続連携） | 既存列の型変更は適用プロセス・履歴データ・下流システムに影響。ALTER ができない、または再作成＋バックフィルになる |

やり直しの典型:

- 試験は通ったが、本番 CDC で型不一致エラー  
- `DATETIMEOFFSET` を日時型だと思って作り、Qlik は文字列で送ってくる  
- `TIMESTAMP`（SQL Server の rowversion）を日時型にしてしまう  
- 桁・精度不足で後から `VARCHAR(50)` → `(200)` や `NUMBER` の精度変更が必要になる  
- 変換表に無い型を仮で `VARCHAR` にしてしまい、システム処理が壊れる  

**移行テーブル文書で型を確定し、CDC開始後は原則その型を変えない。** これが再作業を避ける条件。

## 5. テーブルと View（文書上の扱いを分ける）

お客様の整理に同意する。移行テーブル文書でも対象を分ける。

### テーブル（システム利用・CDC対象）

- CREATE で型を明示する。  
- 変換表に載っている型だけを使う。  
- 誤り = システムエラー・試験無駄・CDC後のやり直し。  
- **文書の主対象。ここで慎重に設計する。**

### View（ユーザ2次利用）

- CREATE で型指定が無く、Snowflake が推論する。  
- 2次利用はほぼユーザ。推論のずれは不便だが、システム停止にはなりにくい。  
- 移行テーブル文書では「View の型は推論に任せる。テーブルと同等の変換表レビューはしない」と明記すれば十分。

同じ工数を View に使わない。議論の焦点はテーブル。

## 7. 移行テーブル文書に書くべきこと（提案）

実装ではなく、**文書の目次案**。これが揃えば型ミスの再作業を相当減らせる。

### 7.1 変換の正（優先順位）

矛盾したとき、どれを採用するか文書に書く。

1. 承認済みの個別例外（列単位）  
2. 保全環境の実測 DDL（Qlik が実際に出した型）  
3. Qlik 公式変換規則に基づく変換表  
4. 表に無い → **作らない（確認待ち）**

公式と保全が違う場合: 保全を「事実」として記録し、採用型は承認者が決める。第三の型をその場で invent しない。

### 7.2 変換表（③の本体）

人間が埋める表。ツール用YAMLではない。

| SQL Server型 | Qlik内部型 | Snowflake型 | 桁・精度の決め方 | 注意（意味の欠落） | 確度 | テーブル使用 |
|---|---|---|---|---|---|---|
| 例: `INT` | INT4 | `NUMBER(38,0)` | 固定 | Qlikは整数を NUMBER(38,0) | 問題なし | 可 |
| 例: `DATETIMEOFFSET` | STRING | `VARCHAR` | 長さは保全で確認 | タイムゾーン付き日時ではない | 要確認 | 可（Qlik準拠） |
| 例: `SQL_VARIANT` | 非サポート | （なし） | — | — | 停止 | 不可 |

確度の意味:

- **問題なし** … 変換表どおり定義してよい  
- **要確認** … 載るが意味・桁にリスク。初出はお客様確認  
- **停止** … 変換表に定義しない。テーブルを作らない  

### 7.3 変換ルール外の措置（今回不足している箇所）

テーブル:

- 変換表に無い型は **推測しない**（`VARCHAR` / `VARIANT` への仮置きもしない）。  
- 該当テーブルは定義を止め、変換表を更新・承認してから作成する。  
- 理由: 仮置きすると試験が通り、CDC後に本修正ができなくなる。

View:

- 推論または警告付きフォールバックを許容してよい（方針として文書に一行書けば足りる）。

### 7.4 CDC開始後の型変更（やり直し防止）

移行テーブル文書に「作った後」も一行で縛る。

- 既存列の **型変更・桁縮小・NOT NULL 強化は原則禁止**。必要なら新列追加または再作成＋バックフィル（変更管理）。  
- 列追加（NULL可）と VARCHAR の桁拡大は、Qlik / Snowflake の確認後に検討可。  
- ソースに新しい未知型の列が付いた場合も、作成時と同じ: **推測して ALTER しない。止めて確認。**

### 7.5 対象範囲の明記

- どのDB・スキーマが in-scope か。  
- 保全がその全部を含むか。含まないなら ②は「サンプル確認」と書く（全件証明と書かない）。  
- View は型レビュー対象外、と書く。

## 8. 間違えやすい型（文書の「注意」列に残すもの）

全部を暗記する必要はない。変換表の注意列用。Qlik の規則を正とする（Snowflake移行ツールの別マッピングと混ぜない）。

システム処理・CDCで特に事故りやすいもの:

| SQL Server | やりがちな誤り | 議論上の扱い（Qlik準拠の方向） |
|---|---|---|
| `TIMESTAMP` / `ROWVERSION` | 日時型にしてしまう | 日時ではない。バイナリ系 |
| `DATETIMEOFFSET` | `TIMESTAMP_TZ` と決め打ち | Qlikは STRING になり得る。公式＋保全で確認 |
| `TIME` | Snowflake `TIME` と決め打ち | Qlikは STRING になり得る。公式＋保全で確認 |
| `DATETIME` / `DATETIME2` | 精度・タイムゾーンを無視 | 精度を変換表に書く |
| `MONEY` / `SMALLMONEY` | 汎用 NUMBER で桁を落とす | 精度（19,4 等）を表に固定 |
| `DECIMAL`/`NUMERIC` の精度 | p>38 を黙って文字列化 | テーブルでは黙って替えない。確認 |
| `VARCHAR(MAX)` / `NVARCHAR(MAX)` / `XML` | 桁・LOB のCDC制限を無視 | 要確認。QlikでCLOB有効が必要かも |
| `UNIQUEIDENTIFIER` | BINARY と VARCHAR が混在 | 変換表で一方に固定 |
| `BIT` | NUMBER(1) と BOOLEAN が混在 | 変換表で一方に固定 |
| UDT（ユーザ定義型） | 名前のまま未定義 | 基底型に戻してから変換表を見る。戻せなければ停止 |
| `SQL_VARIANT` / `CURSOR` / `TABLE` | 適当に VARIANT | Qlik非サポートなら **停止** |
| `GEOGRAPHY` / `GEOMETRY` / `HIERARCHYID` | Snowflake地理型へ勝手に合わせる | 公式＋保全。勝手に最適化しない |

ポイント: 「Snowflakeとして綺麗な型」より **Qlikが実際に出す型** を移行テーブル文書の正とする。ここがずれると、テーブルは正しく見えても CDC で落ちる / 試験が無駄になる。

## 9. 「全ケースをカバーする」の意味

型を40個列挙しても、41個目は出る。全ケースカバーは次の5つが文書にあれば足りる。

1. **既知の型** → 変換表（①②③ + 利用中型の棚卸し）  
2. **未知の型** → 停止して確認（推測しない）  
3. **後から型が変わる** → ALTERしない。変更管理  
4. **載るが意味が違う** → 変換表の「要確認」＋保全実測  
5. **保全に無い対象** → in-scope 外、またはサンプルと明記  

型名の百科事典より、**41個目の型の行き場** を文書に書く方が再作業防止になる。

利用中型の棚卸し（①の前にやると漏れが減る）:

- SQL Server の利用中データ型を一覧する（テーブル列の distinct type）。  
- その一覧がすべて変換表に載っているか見る。  
- 保全に無い型が in-scope にあれば、②だけでは不足、と分かる。

（棚卸しSQLをこの議論で実装する必要はない。方針として「変換表の対象は実在型から取る」と書けばよい。）
