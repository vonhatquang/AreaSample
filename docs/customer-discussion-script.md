# 会議シナリオ：移行テーブルのデータ型

Quang 用。お客様との議論の進め方。実装の話はしない。  
ゴール: 移行テーブル文書に「型の決め方」と「ルール外の措置」を書く方針を揃える。  
成功: Structured Raw の型が、CDC Raw に入っても作り直さない。

**今日決めたいこと（4つだけ）**

1. 変換の正は **Qlik** でよいか（Snowflake公式は桁などのチェックだけ）  
2. SQL Serverにあるが Qlik に無い型は **推測せず、そのテーブルは作らない** でよいか  
3. CDC開始後、既存列の型は **ALTERしない** でよいか  
4. 要確認・ルール外の **承認者はお客様** でよいか  

ベトナムは一覧・突合・変換表の下書き。型の最終判断はお客様。

- 「全部ベトナムがやります」は言わない。  
- View の型を深掘りしない。テーブルの話に戻す。

## Part B — なぜ今型を固めるか（5分）

### 話す内容

> データ型は、SQL Server と Snowflake で名前が違います。間に Qlik があり、Qlik の規則で型が変わります。  
> CDC は、全件コピーではなく、変更分だけ Snowflake に送り続ける方式です。一度走り始めると、列の型を変えるのはテーブルの作り直しに近いです。  
> だから Structured Raw の時点で、Qlik が実際に書く型に合わせてテーブルを定義しておきたい、という理解です。  
> 型を仮で決めて試験が通っても、CDC 開始後に直すと試験が無駄になります。ご指摘のとおりです。

### 例（聞かれたら出す。最初から長く話さない）

> 例: SQL Server の TIME を、Snowflake の時刻型で作ってしまう。Qlik は文字列で送ることがある。テーブルは正しく見えても、CDC で型が合わずやり直し、というパターンです。

### 決めること

なし。認識合わせのみ。

## Part D — 7ステップ（本題・20〜25分）

先に全体を一口で:

> ①②③を次の順で具体化する案です。1〜5が変換表の作り方、6が保全での検定（②のまま）、7がルール外とCDC後の閉じです。

各ステップ: **説明 → 例 → 聞く → 決める**。全部の型の話に入らない。方針だけ。

### Step 1. 現行 SQL Server の CREATE TABLE から、使用中の型を一覧する

**説明**

> まず、対象テーブルの CREATE TABLE を読み、今使っているデータ型を一覧します。  
> テーブル名の一覧ではなく、INT、NVARCHAR、DATETIME2、XML のような型の種類です。  
> Qlik の資料だけ見ると「資料に載っている型」しか分かりません。ルールに無い型は、実際に使っている型を先に出さないと見つかりません。今回のご指摘の前提です。

**例**

> Customer に INT、NVARCHAR、DATETIMEOFFSET がある、という一覧です。何列あるかまで出しておくと、後で漏れに気づけます。View の CREATE はこの一覧に入れません。

**聞くこと**

- 対象はどの DB・スキーマまでか。  
- 今の Structured Raw 対象だけか、将来 CDC に入るテーブルも含めるか。  
- 保全にその範囲は全部あるか。

**決めること**

- [ ] in-scope の範囲（後でメールでも可。今日「全スキーマ / 一部」だけでも可）

**自分がやると言ってよいこと**

> 対象が分かれば、使用中データ型の一覧の下書きは出せます。

---

### Step 2. Qlik / CDC 公式から、型と変換先を一覧する

**説明**

> 次に Qlik の公式で、SQL Server の型が Snowflake の何になるかを書きます。  
> Qlik は二段です。SQL Server 型 → Qlik の内部型 → Snowflake 型。変換先まで取らないとテーブルを作れません。  
> CDC で Snowflake に載る型は、Qlik が変換した結果です。ここを正にしたいです。

**例**

> INT は NUMBER。TIME は時刻型ではなく文字列になることがある。TIMESTAMP（SQL Server）は日時ではなく行バージョン、バイナリ、など。個別の最終型は公式と保全で確認して変換表に書きます。今日は暗記で決めません。

**聞くこと**

- Qlik の製品名とバージョンは（Replicate か、別か）。  
- タスクで型の上書き（グローバル変換）をしているか。しているなら公式デフォルトではなくその設定が正。

**決めること**

- [ ] 正にする Qlik 資料（製品・バージョン）。分からなければ「確認して共有いただく」

**注意**

製品名を間違えて断言しない。分からなければ聞く。

---

### Step 3. 1 と 2 を突合して分類する（マージしない）

**説明**

> 1 と 2 を一つのリストに足すだけにはしません。三つに分けます。  
> **A.** 両方にある → 普通に変換表へ。  
> **B.** SQL Server にあるが Qlik に無い／非サポート → これが今回の「ルール外」。  
> **C.** Qlik にあるが今の DDL に無い → 参考。今はテーブルに使わない。  
> B を A に混ぜて仮の型を付けると、また措置が無くなります。

**例**

> SQL_VARIANT や、分解できないユーザ定義型が B になりやすいです。  
> B の列が一つでもあるテーブルは、型が分からないまま CREATE すると、CDC 後に直せません。なのでそのテーブルは作らず、先に方針を決める、が提案です。

**聞くこと（ここが本丸）**

- B のとき:  
  - (案1) そのテーブルの作成を止めて、変換表を更新してから作る ← **提案**  
  - (案2) その列だけ CDC 対象外にする  
  - (案3) VARCHAR 等で仮置きする ← **非推奨。試験が通ってCDC後に詰まる**

**決めること**

- [ ] 分類 A/B/C で進める  
- [ ] B は案1（停止）か、案2（対象外）か。案3は使わない、と言ってもらう

**反対「仮置きしないと進まない」への返し**

> 仮置きすると Structured Raw の試験は通ります。CDC 開始後に本修正しようとすると ALTER が難しく、ご懸念の再作業になります。進める必要があるテーブルは、B の列を対象外にするか、先に型を決めるか、どちらかが安全だと思います。

---

### Step 4. Snowflake 公式は制約確認だけ。変換の正は Qlik

**説明**

> Snowflake 公式にも SQL Server からのマッピングがあります。ただしあれは「SQL を綺麗に移植する」資料です。  
> 今回は Qlik が CDC で Snowflake に書くので、変換の正は Qlik にしたいです。  
> Snowflake 公式は、Qlik の変換先がそのままで作れるか、桁・精度の上限はどこか、を見るために使います。Qlik と違う型に置き換えません。

**例（短く一つ）**

> DATETIMEOFFSET を Snowflake 推奨のタイムゾーン付き日時で作ると綺麗に見えます。Qlik が文字列で送ると、CDC で型が合いません。綺麗な型が必要なら、Raw の後段で変換する、が安全です。Raw は Qlik に合わせます。

**聞くこと**

- 変換の正を Qlik にしてよいか。  
- システムが「綺麗な型」を Raw に要求するか。要求するなら後段レイヤの話として分ける。

**決めること**

- [ ] **正は Qlik**。Snowflake公式は上限チェックのみ  
- [ ] 綺麗な型は Raw ではなく後段、でよいか

**反対「Snowflakeの型の方がシステムに良い」への返し**

> システム用の型は必要だと思います。ただし CDC が書く層（Raw）と、システムが読む層を分けると、Raw のやり直しを防げます。Raw を綺麗にすると Qlik とずれます。

### Step 5. 変換表を作る（お客様③）

**説明**

> 3 の分類と 2 の Qlik 変換を、人が読む変換表にします。移行テーブル文書の本体です。  
> A は SQL Server型、Qlik内部型、Snowflake型、桁の決め方、注意、確度。  
> B は Snowflake 型を空にして「停止」。  
> C は参考。  
> 確度は、問題なし / 要確認 / 停止、の三つで足りると思います。  
> TIME や DATETIMEOFFSET、MONEY、MAX、XML は載っても意味がずれやすいので、初出は要確認にします。

**聞くこと**

- 要確認の承認者は誰か（お客様側の名前）。  
- 桁（NVARCHAR の長さなど）も変換表にルールとして書く、でよいか。後から桁不足で ALTER すると CDC で痛い。

**決めること**

- [ ] 変換表の列（型、Qlik、Snowflake、桁、確度）でよいか  
- [ ] 要確認の承認者

**自分がやると言ってよいこと**

> 変換表の下書きは作れます。要確認と停止の行は、埋めずにマークして確認します。最終の型はこちらで決めません。

### Step 6. 保全の実測 DDL で検証する（お客様②のまま）

**説明**

> 1〜5 はドキュメントと現行 DDL です。Qlik のタスク設定やバージョンで、公式と実測が違うことがあります。  
> なので保全で、同じテーブルの SQL Server DDL と Snowflake の実測 DDL を並べ、変換表と矛盾がないか見ます。②はそのまま残したいです。  
> 違う場合、保全の実測を「事実」として記録します。どの型を採用するかはご判断いただきたいです。第三の型をその場で作りません。

**聞くこと**

- 保全は in-scope の全スキーマを含むか。含まないなら「サンプル確認」と文書に書く。  
- 差が出たときの採用者は誰か。

**決めること**

- [ ] ②を残す  
- [ ] 公式≠実測のとき、実測を事実として記録し、採用はお客様  
- [ ] 保全の範囲（全件 or サンプル）

**反対「公式だけ見ればよい」への返し**

> 公式とタスクが同じなら差は出ません。差が出たとき CDC で落ちるので、保全で一度見るコストの方が、作り直しより小さいと思います。

---

### Step 7. ルール外は作らない。CDC後は型を ALTER しない

**説明**

> 1〜6 は今ある型の話です。CDC は続くので、明日ソースに新しい型が付くかもしれません。閉じが無いと、また措置が無い、になります。  
> **今:** 変換表に無い型は推測しません。VARCHAR の仮置きもしません。そのテーブルは作らず、表を更新して承認後に作ります。  
> **CDC開始後:** 既存列の型変更・桁縮小は原則 ALTER しません。列追加（NULL可）は変更管理のうえ検討可。未知の新列も、推測して ALTER しません。  
> これが、Raw になると ALTER できない、への答えです。

**聞くこと**

- 停止ルールを移行テーブル文書に書いてよいか。  
- ALTER禁止を書いてよいか。例外（VARCHARの桁拡大だけ可、など）を今日決めるか、後で決めるか。

**決めること**

- [ ] ルール外 → テーブル作成停止（仮置きしない）  
- [ ] CDC後 → 既存列の型は原則変更しない  
- [ ] 例外の扱い（今日 or 後日）

**反対「止めるとスケジュールが」への返し**

> 止めるのはそのテーブル（またはその型が決まるまで）です。A の型だけしかないテーブルは進められます。B があるテーブルだけ先に方針を決める、が全体より安いと思います。

## 想定質問と短い答え

**Q. ベトナムで変換表まで全部やってほしい**  
A. 下書きと突合はやります。Qlikに無い型と、公式と実測が違う型は、こちらで決めるとCDC後に戻せないので、ご判断をお願いしたいです。

**Q. よく分からない型は VARCHAR でよいのでは**  
A. View や一時領域ならあり得ます。システム用テーブルだと試験が通ってCDC後に直せなくなります。ご懸念の再作業そのものです。

**Q. Snowflake の型の方が正しい**  
A. 加工層ではそうできます。Raw は Qlik が書く型に合わせないと CDC が合いません。

**Q. 保全がまだ無い / 一部しか無い**  
A. その範囲はサンプル確認と書きます。残りの型は実測が出るまで要確認のままにします。全部「問題なし」とは書きません。

**Q. この型（例: DATETIMEOFFSET）は何になる**  
A. 今日は決めません。Qlik公式と保全を見て変換表に書きます。要確認ならご判断をお願いします。

**Q. いつまでかかる**  
A. 方針が決まれば、一覧と表の下書きに入れます。期間は対象テーブル数と保全の有無で変わるので、範囲が分かってから出します。（今日は数字を作らない）
